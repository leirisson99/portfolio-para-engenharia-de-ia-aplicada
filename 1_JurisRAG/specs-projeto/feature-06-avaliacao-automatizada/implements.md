- `src/avaliacao/judge_deepeval.py`: `criar_calculador_deepeval` — factory que fecha sobre `FaithfulnessMetric`/`ContextualPrecisionMetric`/`ContextualRecallMetric`/`AnswerRelevancyMetric` do DeepEval, usando `OpenRouterModel` (nativo do DeepEval, compatível com a API da OpenAI) como Judge Model — lê `OPENROUTER_API_KEY` (obrigatória, reaproveitada de F4) e `AVALIACAO_JUDGE_MODEL` (opcional, default `openai/gpt-4o-mini` — RNF02) do ambiente dentro da factory, no mesmo estilo de `rag/geracao.criar_gerador_llm`. Cada chamada de `_calcular` cria sua própria instância de `OpenRouterModel` e passa `async_mode=False` para as 4 métricas (ver "Desvios da spec" — necessário para concorrência segura no Windows). Duplicou o helper `_variavel_obrigatoria` em vez de importar de `rag/geracao.py` — RAG Core e Avaliação de Qualidade são bounded contexts distintos (ver `00-dominio/bounded-contexts.md`), não devem compartilhar módulos internos.
- `src/avaliacao/executar_avaliacao_cli.py`: script batch reutilizável por F7/F8 (specify.md, seção Escopo) — conecta ao Postgres real (F3, uma conexão por thread via `threading.local`, necessária pela concorrência de `executar_avaliacao`), monta o pipeline real (F4: embeddings + retrieval + geração via OpenRouter) e o calculador real do DeepEval, roda `executar_avaliacao` sobre o Golden Dataset completo (`data/golden/casos_golden.jsonl`), persiste em `data/avaliacoes/historico_execucoes.jsonl` e retorna exit code 0/1 conforme `passou` — contrato que F8 vai consumir como gate de CI.
- 51 novos testes em `tests/avaliacao/` (`test_gate.py`, `test_metricas.py`, `test_execucao.py` incluindo 2 testes de concorrência real com `time.sleep`/`threading.Lock`, `test_execucao_integration.py`, `test_historico_execucoes.py`, `test_judge_deepeval.py`), todos com fakes/mocks — nenhum depende de rede, Postgres ou credenciais reais. `pytest` (88 testes no total do projeto), `ruff check .` e `mypy src` passando.

## Desvios da spec
- **RAGAS → DeepEval**: `plan.md` previa "RAGAS ou DeepEval" (ambos permitidos por `spec-main.md`). Na implementação, `ragas==0.4.3` (única versão disponível no momento) falha já no `import ragas` — `ragas/llms/base.py` importa `langchain_community.chat_models.vertexai`, módulo que não existe mais em `langchain-community==0.4.2` (pacote "sunset"/descontinuado). Não é um bug no nosso código nem contornável com import tardio (o `import ragas` de topo já quebra). Troquei para **DeepEval**, que instala e importa limpo neste ambiente e cobre as mesmas 4 métricas mínimas de RN01. `pyproject.toml` atualizado (`ragas` → `deepeval`). Efeito colateral: `deepeval` prende `click<8.4.0`, enquanto `huggingface-hub` (usado por F1/F3) exige `click>=8.4.2` — não há uma versão de `click` que satisfaça as duas âncoras na resolução do pip. Verifiquei em runtime que `click==8.5.0` funciona para ambos (`import deepeval`, `import datasets`, `import huggingface_hub` sem erro) e que a suíte inteira do projeto passa — fiquei com `click==8.5.0`; o aviso do pip é só do resolvedor, não um erro real.
- **Judge Model via OpenRouter, não OpenAI direto**: a ideia inicial era usar `OPENAI_API_KEY` (como o `.env.example` original já sugeria), mas essa chave não estava configurada no ambiente real do usuário — só `OPENROUTER_API_KEY` (de F4). Em vez de exigir uma credencial nova, usei o `OpenRouterModel` nativo do DeepEval (compatível com a API da OpenAI, incluindo fallback automático quando `response_format` estruturado não é aceito por um provedor específico atrás do OpenRouter) apontando para o mesmo `OPENROUTER_API_KEY` — RNF02 (barato) e zero fricção de setup. `.env`/`.env.example` atualizados: removida a menção a `OPENAI_API_KEY`, adicionado `AVALIACAO_JUDGE_MODEL` (default `openai/gpt-4o-mini`).
- **Paralelização por Caso Golden (RNF01)**: a primeira medição real (sequencial, 35 casos) deu **18.46 min** — muito acima do orçamento de 5 min (cada caso dispara 1 geração + 4 métricas, e cada métrica do DeepEval faz várias sub-chamadas de LLM internamente). Paralelizei `executar_avaliacao` com `ThreadPoolExecutor` (I/O-bound, threads bastam). Isso expôs um bug real de concorrência no Windows: `metric.measure()` do DeepEval roda um event loop assíncrono próprio por chamada (`async_mode=True` por padrão); com várias threads rodando loops `ProactorEventLoop` concorrentes, o cliente HTTP assíncrono interno se corrompia entre threads (`RuntimeError: Event loop is closed` / `asyncio.exceptions.InvalidStateError`), derrubando a execução completa. Corrigido criando uma instância nova de `OpenRouterModel` por chamada (evita client HTTP assíncrono compartilhado entre threads/loops) e passando `async_mode=False` nas 4 métricas (evita loops aninhados por thread inteiramente — cada métrica roda de forma síncrona; a concorrência entre Casos Golden já é suficiente). Ainda aparecem tracebacks cosméticos de `RuntimeError: Event loop is closed` no encerramento do processo (cleanup de conexões HTTP assíncronas residuais durante o shutdown do interpretador) — não afetam o resultado nem o exit code, apenas poluem o log; não investiguei mais a fundo por ser puramente cosmético. Com a paralelização, a segunda medição real deu **3.32 min** — dentro do orçamento.
- **Achado de qualidade de retrieval (fora do escopo de F6, registrado para F3/F4/F7)**: para medir RNF01 de verdade, populei o Vector Store real com um corpus de 497 acórdãos do STJ (mesma amostra de 500 documentos que F5 usou para montar o Golden Dataset — todos os 35 `processo_origem` dos Casos Golden confirmados presentes), chunking `Fixa(tamanho=200, overlap=40)` (baseline de F2) e embeddings reais via `sentence-transformers` (F3). Nas duas execuções reais, `context_precision` (~0.03) e `context_recall` (~0.17–0.24) ficaram muito abaixo do threshold (0.85) — o retrieval está trazendo majoritariamente o chunk de abertura ("Vistos e relatados estes autos...", boilerplate quase idêntico em todo acórdão do STJ) de documentos não relacionados à pergunta, não o chunk relevante do documento correto. `faithfulness` ficou alto (~0.92–0.94) porque o LLM de geração corretamente se recusa a responder com base em contexto irrelevante ("o contexto fornecido não discute isso") em vez de alucinar — ou seja, o gate de RN03 está funcionando exatamente como deveria: bloqueou o merge (`passou=false`) diante de uma qualidade de retrieval real que não atende ao mínimo exigido. Isso não é um bug de F6; é uma limitação de retrieval/chunking (F2/F3/F4) que só ficou visível porque F6 agora existe e mede isso de verdade — fica registrado aqui como ponto de partida para uma futura iteração de melhoria (RNF02/dashboard de F7 vai poder mostrar essa evolução ao longo do tempo).
- Scripts usados para popular o corpus real e disparar as execuções de verificação (fetch do HuggingFace, chunking/embedding/indexação, runner do CLI) foram descartáveis, rodados fora do repo (no scratchpad da sessão) — não commitados, mesmo padrão adotado por F4 para sua verificação manual.
- **Correção (2026-08-28)**: `python -m avaliacao.executar_avaliacao_cli` falhava no GitHub Actions com `ModuleNotFoundError: No module named 'deepeval.models.llms.openrouter_model'`, embora funcionasse localmente. Causa: `deepeval` estava sem versão travada em `pyproject.toml` (`pip install -e ".[dev]"` na CI resolve a última versão disponível a cada execução, podendo divergir do que já estava instalado localmente) **e** `judge_deepeval.py` importava de um caminho interno (`deepeval.models.llms.openrouter_model`), mais sujeito a mudar entre versões do que a API pública do pacote. Corrigido: (1) `pyproject.toml` trava `deepeval==4.2.0` (a versão testada); (2) `judge_deepeval.py` passou a importar `from deepeval.models import OpenRouterModel` (caminho público, `OpenRouterModel` é um export de primeira classe de `deepeval.models.__init__`). Suíte completa (105 testes) revalidada após reinstalar as dependências do zero (`pip install -e ".[dev]"`), simulando o que a CI faz.
